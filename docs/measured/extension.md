# Extension：堆红区大小对开销的影响

论文 §4.3 只定性指出更大的红区 `may lead to significant slowdown and increased
memory usage`，但 §4 的性能测量固定在 32 字节，没有给出 redzone 与开销的量化关系。
本实验把 redzone 作为唯一变化因素，量化这条曲线。

负载选择：`retained_heap` 同时持有 20 万个 48 字节对象。第一版实验用的是
`malloc_heavy`（分配后立刻释放），实测 redzone 从 16 到 2048 字节几乎没有任何影响，
因为瞬时存活对象太少、红区占用不会累积。这说明**负载必须能放大被测量的因素**，
否则实验只会得到一个无信息的空结论。

- 生成时间（UTC）：`2026-11-07 05:22:39`
- CPU：`AMD EPYC 9V45 96-Core Processor`；内核 `7.0.0-1019-azure`
- 每档 3 次，报告 mean ± stddev（样本标准差，n-1）
- 固定项：同一机器、同一 `bench.c`、gcc -O2、`quarantine_size_mb=0`、`malloc_context_size=0`
- 唯一变化项：`ASAN_OPTIONS=redzone=<N>`
- commit：`f59681c`

## 解读要点

1. 红区每翻一倍，每个分配块两侧各多占一倍空间，因此 VmHWM 近似线性增长；
   对 malloc 密集负载，这部分增长会直接转化为分配器元数据压力与缓存压力。
2. 时间开销主要来自"红区毒化 + 影子内存写入"的面积变大，而非插桩检查本身，
   所以增长幅度显著小于内存。
3. 与论文 §4.3 的定性描述一致：更大红区换来更大的可检出越界距离，代价是
   时间与内存；论文在 Chromium 上坚持默认值，并说明"增大这三个参数并未提升
   找 bug 的能力"，本实验的时间/内存曲线为这条经验判断补上了量化依据。
